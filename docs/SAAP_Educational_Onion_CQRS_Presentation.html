مستند ارائه پروژه SAAP Educational

موضوع: ساخت یک پروژه ASP.NET Core Web API با معماری Onion، الگوی CQRS، استفاده از MediatR، و ایجاد abstractionهای مشترک برای mediator و repositoryها.

خلاصه کاری که انجام شد

یک solution با نام SAAP.Educational ساخته شد و پروژه‌ها به پنج لایه تقسیم شدند: Domain، Application، Shared، Infrastructure و Api. هدف این ساختار این است که منطق اصلی برنامه از جزئیات فنی مثل دیتابیس، وب API و کتابخانه‌ها مستقل بماند.

برای اینکه مسیر استفاده از CQRS واضح باشد، یک نمونه ساده روی موجودیت Course ساخته شد. این نمونه شامل query برای گرفتن لیست دوره‌ها، query برای گرفتن یک دوره با شناسه، command برای ساخت دوره جدید، handlerها، DTO، controller و repositoryهای in-memory است.

چرا معماری Onion؟

معماری Onion برنامه را به لایه‌هایی تقسیم می‌کند که وابستگی‌ها از بیرون به داخل حرکت می‌کنند. مرکز معماری، Domain است؛ یعنی قوانین اصلی کسب‌وکار. لایه‌های بیرونی مثل Infrastructure و Api نباید منطق اصلی را آلوده کنند.

مزیتتوضیح قابل ارائه
استقلال DomainDomain به دیتابیس، وب API یا فریم‌ورک وابسته نیست؛ بنابراین تغییر تکنولوژی بیرونی باعث تغییر منطق اصلی نمی‌شود.
تست‌پذیری بهترچون منطق use caseها در Application و قوانین در Domain جدا هستند، می‌توان آن‌ها را بدون اجرای API یا دیتابیس تست کرد.
قابل توسعه بودنبعدا می‌توان دیتابیس واقعی، message broker یا سرویس خارجی اضافه کرد بدون اینکه controllerها یا Domain بهم بریزند.
کنترل وابستگی‌هاApi فقط نقش ورودی سیستم را دارد و Infrastructure فقط پیاده‌سازی جزئیات فنی را انجام می‌دهد.

چرا CQRS؟

CQRS مخفف Command Query Responsibility Segregation است. یعنی عملیات خواندن و نوشتن را از هم جدا می‌کنیم. Query فقط داده می‌خواند و وضعیت سیستم را تغییر نمی‌دهد. Command وضعیت سیستم را تغییر می‌دهد؛ مثلا ساخت، ویرایش یا حذف.

نوع عملیاتدر پروژههدف
QueryListCoursesQuery و GetCourseByIdQueryدریافت داده بدون تغییر وضعیت سیستم
CommandCreateCourseCommandایجاد تغییر در سیستم و ذخیره نتیجه

مزیت CQRS این است که کد خواندن و نوشتن با هم قاطی نمی‌شود. در پروژه‌های بزرگ، queryها معمولا نیاز به projection، paging، caching و optimization دارند؛ اما commandها بیشتر روی validation، business rule و transaction تمرکز می‌کنند.

چرا MediatR؟

MediatR کمک می‌کند controller مستقیما handlerها یا سرویس‌های مختلف را صدا نزند. Controller فقط یک request مثل command یا query می‌سازد و آن را به mediator می‌دهد. MediatR handler مناسب را پیدا و اجرا می‌کند.

در این پروژه یک wrapper مشترک با نام IApplicationMediator ساخته شد تا بقیه تیم مجبور نباشند همه جا مستقیم با IMediator کار کنند. این کار باعث می‌شود وابستگی به کتابخانه MediatR در سطح پروژه کنترل‌شده‌تر باشد.

CoursesController.cs

public sealed class CoursesController : ControllerBase
{
    private readonly IApplicationMediator _mediator;

    public CoursesController(IApplicationMediator mediator)
    {
        _mediator = mediator;
    }

    [HttpGet]
    public async Task<ActionResult<IReadOnlyList<CourseDto>>> List(CancellationToken cancellationToken)
    {
        var courses = await _mediator.QueryAsync(new ListCoursesQuery(), cancellationToken);
        return Ok(courses);
    }

    [HttpGet("{id:guid}")]
    public async Task<ActionResult<CourseDto>> GetById(Guid id, CancellationToken cancellationToken)
    {
        var course = await _mediator.QueryAsync(new GetCourseByIdQuery(id), cancellationToken);
        return course is null ? NotFound() : Ok(course);
    }

    [HttpPost]
    public async Task<ActionResult<CourseDto>> Create(CreateCourseRequest request, CancellationToken cancellationToken)
    {
        var course = await _mediator.SendAsync(
            new CreateCourseCommand(request.Title, request.Description),
            cancellationToken);

        return CreatedAtAction(nameof(GetById), new { id = course.Id }, course);
    }
}

ICommandHandler.cs

public interface ICommandHandler<in TCommand> : IRequestHandler<TCommand>
    where TCommand : ICommand;

public interface ICommandHandler<in TCommand, TResponse> : IRequestHandler<TCommand, TResponse>
    where TCommand : ICommand<TResponse>;

این فایل handlerهای مربوط به command را استاندارد می‌کند. به جای اینکه تیم مستقیما همه جا IRequestHandler بنویسد، از abstraction مخصوص پروژه استفاده می‌کند. constraintها تضمین می‌کنند handler فقط برای command معتبر نوشته شود.

IQuery.cs و IQueryHandler.cs

public interface IQuery<out TResponse> : IRequest<TResponse>;

public interface IQueryHandler<in TQuery, TResponse> : IRequestHandler<TQuery, TResponse>
    where TQuery : IQuery<TResponse>;

Query همیشه خروجی دارد، چون هدفش خواندن داده است. Handler آن نیز فقط query معتبر را می‌پذیرد. این جداسازی کمک می‌کند خواندن‌ها و نوشتن‌ها از سطح type system جدا شوند.

IApplicationMediator.cs

public interface IApplicationMediator
{
    Task SendAsync(ICommand command, CancellationToken cancellationToken = default);

    Task<TResponse> SendAsync<TResponse>(
        ICommand<TResponse> command,
        CancellationToken cancellationToken = default);

    Task<TResponse> QueryAsync<TResponse>(
        IQuery<TResponse> query,
        CancellationToken cancellationToken = default);
}
متدتوضیح
SendAsync(ICommand)برای commandهایی که خروجی ندارند.
SendAsync<TResponse>برای commandهایی که خروجی دارند، مثل ساخت Course.
QueryAsync<TResponse>برای queryها. نام جداگانه باعث خوانایی بهتر کد controller می‌شود.

ICommandRepository.cs

public interface ICommandRepository<TEntity, in TKey>
    where TEntity : class
    where TKey : notnull
{
    Task AddAsync(TEntity entity, CancellationToken cancellationToken = default);
    void Update(TEntity entity);
    void Remove(TEntity entity);
    Task<int> SaveChangesAsync(CancellationToken cancellationToken = default);
}

این interface مخصوص عملیات نوشتن است. متدهای Add، Update، Remove و SaveChanges در سمت command استفاده می‌شوند. generic بودن آن باعث می‌شود برای entityهای مختلف مثل Course، Student یا Lesson قابل استفاده باشد.

IQueryRepository.cs

public interface IQueryRepository<TEntity, in TKey>
    where TEntity : class
    where TKey : notnull
{
    Task<TEntity?> GetByIdAsync(TKey id, CancellationToken cancellationToken = default);
    Task<IReadOnlyList<TEntity>> ListAsync(CancellationToken cancellationToken = default);
}

این interface مخصوص خواندن است. Query side اجازه تغییر entity را نمی‌دهد و خروجی لیست را به صورت read-only برمی‌گرداند. این همان تفکیک CQRS در لایه persistence abstraction است.

Entity.cs

public abstract class Entity<TKey>
    where TKey : notnull
{
    protected Entity(TKey id)
    {
        Id = id;
    }

    public TKey Id { get; protected init; }
}

این کلاس پایه برای entityهای دامنه است. هر entity یک شناسه دارد. constructor محافظت‌شده است تا فقط کلاس‌های فرزند بتوانند آن را صدا بزنند. protected init یعنی شناسه از بیرون آزادانه قابل تغییر نیست.

Course.cs

public sealed class Course : Entity<Guid>
{
    private Course(Guid id, string title, string description)
        : base(id)
    {
        Title = title;
        Description = description;
    }

    public string Title { get; private set; }
    public string Description { get; private set; }

    public static Course Create(string title, string description)
    {
        return new Course(Guid.NewGuid(), title, description);
    }
}

Course نمونه entity دامنه است. constructor آن private است تا ساخت entity از مسیر کنترل‌شده انجام شود. متد static Create نقطه رسمی ساخت Course است و شناسه جدید تولید می‌کند. setterها private هستند تا تغییرات دامنه بعدا فقط از طریق متدهای رفتاری کنترل شوند.

Application DependencyInjection.cs

public static IServiceCollection AddApplication(this IServiceCollection services)
{
    services.AddMediatR(configuration =>
    {
        configuration.RegisterServicesFromAssembly(typeof(DependencyInjection).Assembly);
    });

    services.AddScoped<IApplicationMediator, ApplicationMediator>();

    return services;
}

این extension method ثبت سرویس‌های لایه Application را یکجا انجام می‌دهد. MediatR کل assembly مربوط به Application را scan می‌کند و handlerها را پیدا می‌کند. سپس wrapper پروژه یعنی IApplicationMediator به پیاده‌سازی ApplicationMediator وصل می‌شود.

ApplicationMediator.cs

internal sealed class ApplicationMediator : IApplicationMediator
{
    private readonly IMediator _mediator;

    public ApplicationMediator(IMediator mediator)
    {
        _mediator = mediator;
    }

    public Task SendAsync(ICommand command, CancellationToken cancellationToken = default)
    {
        return _mediator.Send(command, cancellationToken);
    }

    public Task<TResponse> SendAsync<TResponse>(ICommand<TResponse> command, CancellationToken cancellationToken = default)
    {
        return _mediator.Send(command, cancellationToken);
    }

    public Task<TResponse> QueryAsync<TResponse>(IQuery<TResponse> query, CancellationToken cancellationToken = default)
    {
        return _mediator.Send(query, cancellationToken);
    }
}

این کلاس adapter بین abstraction خودمان و MediatR است. internal است چون بیرون از Application نباید مستقیم با آن کار کند. controller فقط interface مشترک را می‌شناسد.

CourseDto.cs

public sealed record CourseDto(Guid Id, string Title, string Description);

DTO خروجی API است. به جای برگرداندن مستقیم entity دامنه، داده مورد نیاز client را در یک record سبک و immutable می‌فرستیم.

ListCoursesQuery.cs و Handler آن

public sealed record ListCoursesQuery : IQuery<IReadOnlyList<CourseDto>>;

internal sealed class ListCoursesQueryHandler : IQueryHandler<ListCoursesQuery, IReadOnlyList<CourseDto>>
{
    private readonly IQueryRepository<Course, Guid> _courseRepository;

    public async Task<IReadOnlyList<CourseDto>> Handle(ListCoursesQuery request, CancellationToken cancellationToken)
    {
        var courses = await _courseRepository.ListAsync(cancellationToken);

        return courses
            .Select(course => new CourseDto(course.Id, course.Title, course.Description))
            .ToList();
    }
}

Query فقط درخواست خواندن لیست است. Handler از IQueryRepository استفاده می‌کند، داده‌های Course را می‌خواند و آن‌ها را به CourseDto تبدیل می‌کند. این mapping باعث می‌شود entity داخلی مستقیم از API بیرون نرود.

GetCourseByIdQuery.cs و Handler آن

public sealed record GetCourseByIdQuery(Guid CourseId) : IQuery<CourseDto?>;

public async Task<CourseDto?> Handle(GetCourseByIdQuery request, CancellationToken cancellationToken)
{
    var course = await _courseRepository.GetByIdAsync(request.CourseId, cancellationToken);

    return course is null
        ? null
        : new CourseDto(course.Id, course.Title, course.Description);
}

این query شناسه دوره را دریافت می‌کند. خروجی nullable است چون ممکن است دوره‌ای با آن شناسه وجود نداشته باشد. Handler در صورت نبود داده null برمی‌گرداند و controller آن را به 404 تبدیل می‌کند.

CreateCourseCommand.cs و Handler آن

public sealed record CreateCourseCommand(string Title, string Description) : ICommand<CourseDto>;

public async Task<CourseDto> Handle(CreateCourseCommand request, CancellationToken cancellationToken)
{
    var course = Course.Create(request.Title, request.Description);

    await _courseRepository.AddAsync(course, cancellationToken);
    await _courseRepository.SaveChangesAsync(cancellationToken);

    return new CourseDto(course.Id, course.Title, course.Description);
}

این command قصد تغییر وضعیت سیستم را نشان می‌دهد: ساخت Course جدید. Handler از متد factory داخل Domain استفاده می‌کند، سپس از ICommandRepository برای ذخیره استفاده می‌کند. در پایان DTO ساخته‌شده برگردانده می‌شود.

public static IServiceCollection AddInfrastructure(this IServiceCollection services)
{

InMemoryCourseQueryRepository.cs

public Task<Course?> GetByIdAsync(Guid id, CancellationToken cancellationToken = default)
{
    return Task.FromResult(_storage.Courses.FirstOrDefault(course => course.Id == id));
}

public Task<IReadOnlyList<Course>> ListAsync(CancellationToken cancellationToken = default)
{
    return Task.FromResult<IReadOnlyList<Course>>(_storage.Courses);
}

این repository فقط عملیات خواندن دارد. GetByIdAsync یک دوره را با شناسه پیدا می‌کند و ListAsync کل لیست را برمی‌گرداند. async بودن signature باعث می‌شود بعدا با دیتابیس واقعی بدون تغییر contract هماهنگ شود.

InMemoryCourseCommandRepository.cs

public Task AddAsync(Course entity, CancellationToken cancellationToken = default)
{
    _storage.Courses.Add(entity);
    return Task.CompletedTask;
}

public void Update(Course entity)
{
    var index = _storage.Courses.FindIndex(course => course.Id == entity.Id);
    if (index >= 0)
    {
        _storage.Courses[index] = entity;
    }
}

public void Remove(Course entity)
{
    _storage.Courses.RemoveAll(course => course.Id == entity.Id);
}

public Task<int> SaveChangesAsync(CancellationToken cancellationToken = default)
{
    return Task.FromResult(1);
}

این repository فقط عملیات نوشتن دارد. Add موجودیت را اضافه می‌کند، Update آیتم هم‌شناسه را جایگزین می‌کند، Remove آیتم را حذف می‌کند، و SaveChanges فعلا مقدار 1 برمی‌گرداند چون ذخیره‌سازی واقعی نداریم. در EF Core، همین متد می‌تواند به DbContext.SaveChangesAsync وصل شود.

نکات مهم برای ارائه

  • Controllerها نباید business logic داشته باشند؛ فقط request HTTP را به command/query تبدیل می‌کنند.
  • Application محل use caseهاست؛ هر use case با یک command یا query و handler مربوطه پیاده‌سازی می‌شود.
  • Domain مستقل‌ترین لایه است و نباید به Infrastructure یا Api وابسته شود.
  • Shared محل abstractionهای مشترک است؛ اما نباید تبدیل به محل ریختن همه چیز شود. فقط قراردادهای عمومی و قابل استفاده مشترک باید آنجا باشند.
  • Infrastructure جزئیات فنی را پیاده‌سازی می‌کند؛ امروز in-memory است، فردا می‌تواند SQL Server، MongoDB یا سرویس خارجی باشد.
  • MediatR coupling بین controller و handler را کم می‌کند و مسیر افزودن pipeline behavior مثل validation، logging و transaction را باز می‌گذارد.
